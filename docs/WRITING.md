# 아티클 작성 가이드

crit 아티클의 품질 기준. 파일 포맷/스키마는 [AGENT.md](./AGENT.md),
이 문서는 **무엇을 어떻게 쓰는가**를 다룬다.

## 대원칙

> 글의 형태는 내용이 결정하고, 사실의 순서는 원문이 결정한다.

같은 틀을 반복하면 읽는 사람은 세 번째 글부터 스크롤만 한다. 소식 한 줄이면
세 문단으로 늘리지 말고, 규칙 40개짜리 레퍼런스면 요약해서 죽이지 마라.

1. **먼저 원문을 정확히 전달한다.** 주장, 사례, 숫자, 고유명사, 전개 순서와
   원문 안의 긴장을 보존한다. 요약 때문에 저자의 논리가 다른 글이 되면 실패다.
2. **사실과 crit의 판단을 분리한다.** 본문은 source-faithful summary이고,
   `crit의 관점`은 별도 섹션이다. 해석을 원문의 주장처럼 섞지 않는다.
3. **읽고 나서 뭔가 달라져야 한다.** 새로 알게 되거나, 쓸 도구가 생기거나,
   관점이 바뀌어야 함.
4. **확인된 것만 쓴다.** 수치·날짜·기능명은 원문에서 확인된 것만. 불확실하면 뺀다.

## 1. 포맷 선택 (`format` frontmatter)

글의 성격에 맞는 레이아웃을 고른다. 이걸 먼저 정하고 쓴다.

| format | 언제 | 렌더링 | 분량 |
|---|---|---|---|
| `brief` (기본) | 소식 하나, 관점 하나 | 일반 본문 | 300~700자 |
| `deep` | 깊게 파는 글, 번역·해설, 인터뷰 | 목차 + 읽는 시간 | 1,500자~ |
| `rules` | 규칙/팁/체크리스트 모음 | 번호 카드 + 읽는 시간 | 항목 수에 비례 |
| `showcase` | 브랜드 런칭, 리브랜드 케이스 스터디 | 히어로 + 풀블리드 비주얼 | 이미지가 주, 텍스트가 종 |

### `brief` — 대부분의 뉴스

핵심만. **섹션 제목을 매번 똑같이 쓰지 마라.** 소식에 따라 필요한 섹션이 다르다.
짧은 소식이면 섹션을 아예 나누지 않고 3~4문단으로 흘려 써도 된다.

### `deep` — 긴 글

`##` 섹션이 3개 이상이면 목차가 자동 생성된다. 섹션 제목은 내용을 알려주는
구체적인 문장으로 (❌ "배경" → ✅ "왜 지금 다시 그리드인가").

원문이 긴 아티클을 소개할 때도 핵심 논증이 이어지는 순서를 보존한다. 모든 문단을
같은 비율로 줄일 필요는 없지만, 중간 사례를 덜어낸 탓에 결론의 근거가 사라지거나
저자의 긴장이 한쪽 결론으로 평평해지면 안 된다.

### `rules` — 레퍼런스형

`### 제목` 하나가 카드 하나가 되고 번호가 자동으로 붙는다.

```markdown
디자인 결정이 막힐 때 꺼내 쓰는 규칙들입니다.

### 아이콘은 텍스트보다 시각적으로 가벼워야 한다

같은 크기라면 아이콘이 더 무겁게 보입니다. 광학적으로 맞추세요.

![왼쪽: 같은 크기, 오른쪽: 광학 보정](image.png)

### 그림자는 한 방향에서만 온다
...
```

- 카드 제목은 **규칙 자체를 문장으로** 쓴다 (❌ "아이콘 크기" → ✅ "아이콘은
  텍스트보다 시각적으로 가벼워야 한다")
- 설명은 2~3문장. 길어지면 `deep`으로 쓸 글이다.
- 원문의 항목을 전부 옮기지 말고 **가장 유용한 것만 골라라.** 40개 중 12개를
  고르고 "나머지는 원문에서"가 정직하다.

### `showcase` — 브랜드 런칭 · 케이스 스터디

이미지와 영상이 본문인 포맷이다. 텍스트는 비주얼 사이를 잇는 역할.

```yaml
format: showcase
hero: "https://.../hero.jpg"        # 상단 대표 이미지 (필수급)
credits:                            # 하단 크레딧 블록
  - "브랜드 디자인 — Koto"
  - "클라이언트 — Coda"
```

- **히어로 이미지가 첫인상**이다. 로고 단독 컷보다 적용 사례(패키지, 사이니지,
  화면)가 강하다. 4:3으로 크롭되니 중요한 요소를 가운데에.
- 섹션마다 비주얼 하나 이상. 텍스트 두 문단 연속이면 리듬이 죽는다.
- 이미지·영상은 모바일에서 화면 폭을 꽉 채워 렌더된다(풀블리드).
- 구성 순서 권장: **히어로 → 로고/워드마크 → 전략(왜 바뀌었나) → 시스템 적용 →
  모션 → 배울 점**. 스튜디오 케이스 스터디를 그대로 번역하지 말고, 우리 독자가
  가져갈 것을 마지막에 남긴다.
- 브랜드 자산 이미지는 **공식 프레스킷 / 스튜디오 프로젝트 페이지** 출처만 쓰고
  `credits`에 밝힌다.

에셋 URL은 손으로 찾지 말고 추출 도구를 쓴다:

```bash
npm run assets:find -- https://www.pentagram.com/work/pfizer
```

og:image(히어로 후보), srcset 최대 해상도, lazy `data-src`, `<video>`, 인라인
JSON의 에셋까지 뽑아준다. 네트워크가 막힌 환경이면 GitHub Actions의
**Find Assets** 워크플로를 수동 실행해 요약에서 URL을 받는다.

> [!WARNING]
> 리브랜드 시점을 확인하라. 스튜디오가 케이스 스터디를 늦게 공개하는 일이 흔하다.
> 2년 전 작업을 "런칭했습니다"로 쓰면 안 된다 — 케이스 스터디로 쓰면 된다.

## 2. 기계적으로 쓰지 않기

다음은 실제로 우리가 저지른 실수들이다.

### ❌ 모든 글이 같은 뼈대

```
## 무엇이 바뀌었나
## 디자이너에게 왜 중요한가
## 지금 해볼 것
```

세 글 연속 이러면 독자는 패턴을 알아채고 읽기를 멈춘다. 섹션은 그 글에
필요한 것만, 그 글에 맞는 이름으로.

### ❌ 불릿으로 도망가기

핵심 주장을 불릿 3개로 나열하면 생각의 연결이 사라진다. **인과관계가 있으면
문장으로 이어 써라.** 불릿은 병렬적인 항목(기능 목록, 비교)에만.

### ❌ 내용 없는 마무리

"앞으로가 주목됩니다", "귀추가 주목됩니다", "함께 지켜봅시다" — 아무 정보가
없다. 마무리에 쓸 말이 없으면 마무리를 쓰지 마라. 마지막 문단이 그냥 끝나도 된다.

### ❌ 원문을 임의로 재조립

원문을 읽기 좋게 만든다는 이유로 순서를 바꾸면 저자가 쌓은 인과관계가 쉽게 깨진다.
섹션 수는 줄일 수 있지만 주장 → 사례 → 반전 → 결론의 순서는 보존한다. 국내 맥락이나
crit의 해석은 원문 요약 안에 끼워 넣지 말고 뒤의 별도 섹션으로 보낸다.

### ✅ 대신 이렇게

- **구체적인 숫자와 이름**으로: "성능이 개선됐다" → "빌드가 8초에서 3초로"
- **반대 의견도 함께**: 원문이 주장이면 그 주장의 약한 지점을 한 문장이라도
- **국내 맥락 보충**: 해외 글에는 없지만 한국 실무에서 걸리는 지점
- **인용은 인용으로**: 원문의 좋은 문장은 압축하지 말고 `>` 로 그대로 (번역해서)

## 3. 리치 콘텐츠

### 이미지 + 캡션

```markdown
![alt 텍스트 — 내용 설명](https://example.com/img.png "캡션으로 보일 문구")
```

- alt는 항상 내용 설명 (스크린리더·SEO). `title`을 주면 캡션이 되고,
  없으면 alt가 캡션으로 쓰인다.
- **출처가 명확한 이미지만**: 공식 블로그/프레스킷, 오픈 라이선스, 직접 캡처.
  원문 이미지를 통째로 옮겨 붙이지 않는다.

### Before / After 비교

이미지 2장을 **한 문단에** 나란히 쓰면 2열 그리드로 렌더된다.

```markdown
![Before — 간격이 균일해서 그룹이 안 보임](before.png) ![After — 8/16 간격으로 그룹 분리](after.png)
```

alt가 각 이미지 아래 라벨로 들어간다. `rules` 포맷과 궁합이 좋다.

### 갤러리

이미지 **3장 이상**을 한 문단에 쓰면 갤러리 그리드가 된다 (모바일 2열, 태블릿 3열).
`showcase` 포맷의 시스템 적용 컷에 쓴다.

### 영상 · 유튜브 · X · 링크 카드

URL을 **한 줄에 단독으로** 쓰면 자동 변환된다.

| URL | 결과 |
|---|---|
| `youtube.com/watch?v=…`, `youtu.be/…` | 플레이어 임베드 |
| `x.com/…/status/…` | 포스트 임베드 |
| `.mp4`, `.webm`, `.mov` | 자동재생·루프·무음 비디오 (컨트롤 포함) |
| 그 외 모든 URL | 썸네일 링크 카드 (OG 추출) |

모션 그래픽·로고 애니메이션은 유튜브보다 직접 mp4가 낫다 — 재생 버튼 없이 바로
움직이고 UI 잡음이 없다.

- 문장 속 링크는 일반 링크로 남는다. 카드는 강조할 1~2개만.
- `source_url`과 같은 링크를 본문 카드로 또 넣지 않는다 (상단 "원문 보기"와 중복).

### 콜아웃

```markdown
> [!TIP]
> 팀 라이브러리가 정리돼 있을수록 결과가 좋아집니다.
```

`[!TIP]` 팁 · `[!NOTE]` 참고 · `[!WARNING]` 주의 · `[!IMPORTANT]` 중요.
글마다 하나 정도. 남용하면 본문이 다 상자가 된다.

### 표

비교에 쓴다. **열 4개 이하** — 모바일에서 가로 스크롤된다.

## 4. 초안으로 두기

에셋이 아직 없거나 사람 검수가 필요하면 `draft: true`로 두면 된다.
피드·사이트맵·검색엔진에서 빠지고 URL로만 열린다. 완성되면 플래그를 지운다.

```yaml
draft: true
```

검수 목록은 **`/drafts`** 에서 볼 수 있다. 발행 전에 손봐야 할 것(placeholder
이미지, "교체 필요" 표시, 히어로 누락, 원문 링크 누락)이 경고 칩으로 표시되니
칩이 하나도 없을 때 플래그를 지우면 된다.

## 5. 제목과 요약

- **title** (120자): 궁금하게 만들되 낚시 금지. 무엇에 대한 글인지 알 수 있게.
- **summary** (300자): 피드 카드에 노출된다. 본문 첫 문장 복사 금지 —
  독립적으로 읽히고, 클릭할 이유를 담아야 한다.

## 6. 문체 — `style: geeknews`

`format`은 화면 레이아웃이고 `style`은 문장의 리듬이다. 둘을 섞지 않는다.

- 독자가 **30초 안에 핵심을 파악**할 수 있게 summary에 결론 3~5개를 `•` 불릿으로 둔다.
- 본문은 짧은 문단과 논지형 소제목을 사용한다. 제목은 `배경`, `시사점`보다
  `좋은 인터페이스가 오히려 판단을 숨긴다`처럼 내용을 먼저 말한다.
- 건조한 메모체를 기본으로 `-다`, `-함`, `-임`을 문맥에 맞게 섞는다. 문장마다
  종결형을 교대하는 기계적인 리듬은 피한다.
- 한국어 제목은 직역하지 않는다. 먼저 원문의 맥락과 중심 뜻을 이해한 뒤 자연스럽게
  옮기되, 뜻과 긴장은 바꾸지 않는다.
- 도구·기능 고유명사는 원문 유지 (Figma Motion, Code Layers). 필요한 첫 지점에만
  한국어와 영어를 함께 적는다.
- 과장 금지: `혁명적`, `게임체인저`, `필수` 대신 무엇이 구체적으로 달라지는지 쓴다.
- 이모지, 상투적인 팀 조언, `앞으로가 기대된다` 같은 빈 결론을 쓰지 않는다.
- 한 문단에 한 생각. 문단은 대체로 2~4문장이고, 병렬 정보에만 불릿을 사용한다.
- 원문이 편지·인터뷰·에세이처럼 화자의 목소리가 중요한 글이면 메모체보다 그 목소리와
  전개를 우선한다. 스타일 때문에 원문을 모두 같은 글처럼 만들지 않는다.

## 7. 원문과 crit의 관점을 나누는 법

본문 마지막에는 원문과 분리된 `## crit의 관점` 하나만 둔다. 별도의 비평 소제목이나
유형 이름을 붙이지 않고, 이 글을 읽고 crit가 중요하다고 판단한 생각 하나를 1~3문장으로
간결하게 쓴다. 원문의 장점을 의례적으로 칭찬한 뒤 반론을 나열하는 공식도 만들지 않는다.

`균형이 필요하다`, `팀에 맞게 적용하자`처럼 어느 글에도 붙일 수 있는 문장은 피한다.
대신 원문의 어떤 주장이나 장면에서 나온 생각인지 구체적으로 밝히되, 새로운 자료나
원문에 없는 결론을 덧붙이지 않는다.

### 작성 순서

1. 원문을 직접 읽고 제목, 저자, 날짜, 사례, 숫자, 인용을 메모한다.
2. 원문의 전개 순서대로 주장 지도를 만든다.
3. 그 지도만으로 source-faithful body를 쓴다. 이 단계에서는 crit 해석을 넣지 않는다.
4. 원문과 대조해 누락·과장·순서 변경을 확인한다.
5. 마지막에만 crit의 관점을 쓰고, 사실 문장과 의견 문장을 다시 구분한다.
6. 자연스러운 한국어와 `geeknews` 리듬으로 2차 윤문한다. 윤문 때문에 사실을 바꾸지 않는다.
