# 에이전트 포스팅 가이드

이 문서는 **뉴스/채용 큐레이션 에이전트**가 crit에 콘텐츠를 게시하는 방법을 정의합니다.
사람이 읽어도 되지만, 1차 독자는 매일 실행되는 AI 에이전트입니다.

## 원칙

- **콘텐츠 = 파일 = git 커밋.** DB 쓰기, API 호출 없이 `content/` 아래 파일을 추가하고
  커밋/푸시하면 게시가 완료됩니다. 배포(Vercel 등)는 push에 연동됩니다.
- 게시 전 반드시 `npm run validate` 를 실행해 통과해야 합니다. CI에서도 같은 검증이 돌며,
  실패한 커밋은 배포되지 않습니다.
- 하루 아티클 수는 카테고리 합산 **3~7개**를 권장합니다. 양보다 큐레이션 밀도가 중요합니다.

## 1. 아티클 게시

### 파일 위치와 이름

```
content/articles/YYYY-MM-DD-kebab-case-slug.md
```

- 날짜는 게시일(KST 기준). frontmatter의 `date`와 반드시 일치해야 합니다.
- slug는 소문자 영문/숫자/하이픈만. 내용을 짐작할 수 있게 짓습니다.

### frontmatter 스키마 (`lib/schema.ts`의 zod 스키마가 원본)

```yaml
---
title: "제목 (120자 이내)"                # 필수
summary: "한두 문장 요약 (300자 이내)"     # 필수. 피드 카드에 노출됨
category: design                          # 필수. 아래 카테고리 중 하나
format: brief                             # 선택. brief(기본) | deep | rules | showcase
tags: [figma, ai]                         # 선택. 최대 8개
date: "2026-07-28"                        # 필수. YYYY-MM-DD
source_url: "https://..."                 # 선택. 외부 원문이 있으면 필수 권장
source_name: "Figma Blog"                 # 선택. 출처 표기
thumbnail: "https://..."                  # 선택. 피드 카드 썸네일
hero: "https://..."                       # 선택. 상단 대표 이미지 (showcase 권장)
credits: ["브랜드 디자인 — Koto"]          # 선택. 하단 크레딧 (showcase)
draft: false                              # 선택. true면 피드·사이트맵 제외
author: "crit agent"                      # 선택. 기본값 "crit agent"
---
```

### 카테고리

| 값 | 표시명 | 다루는 것 |
|---|---|---|
| `design` | 디자인 | UX/UI, 디자인 시스템, 인터랙션, 시각 디자인 관점 |
| `ai-design` | AI × 디자인 | AI가 디자인 업무·도구·판단 기준을 바꾸는 사례 |
| `tools` | 툴 | 디자인/프로토타이핑/리서치 도구 추천, 비교, 활용법 |
| `case-study` | 케이스 | 브랜드·제품·캠페인 사례 분석 |
| `career` | 커리어 | 포트폴리오, 채용, 커리어 전략 |

### 본문 작성 규칙

- **[WRITING.md](./WRITING.md)를 따릅니다** — 포맷 선택 기준, 리치 콘텐츠 문법,
  기계적 글쓰기 안티패턴, 문체가 정의되어 있습니다.
- 특히 중요: **모든 글에 같은 섹션 뼈대를 쓰지 않습니다.** 글의 성격에 맞는
  `format`을 고르고, 섹션은 그 글에 필요한 것만 그 글에 맞는 이름으로 씁니다.
- 요약하면: 마크다운(GFM), `h2(##)`부터 시작, 원문 링크 필수, 유튜브/X/일반 URL을
  단독 줄에 쓰면 각각 플레이어·포스트·썸네일 카드로 렌더링됩니다.
  `rules` 포맷에서는 `### 제목`이 번호 카드가 됩니다.

## 2. 채용 공고 게시

### 파일 위치와 이름

```
content/jobs/YYYY-MM-DD.json
```

하루치 공고를 파일 하나에 담습니다. 같은 날 재실행하면 기존 파일을 덮어씁니다.

### 스키마

```json
{
  "date": "2026-07-28",
  "jobs": [
    {
      "id": "2026-07-28-company-role",     // 필수, 전체 파일에서 유일해야 함
      "company": "회사명",                  // 필수
      "title": "포지션명",                  // 필수
      "location": "서울 강남 / 원격 가능",   // 필수
      "employment_type": "full-time",       // full-time | contract | freelance | internship
      "experience": "경력 3년+",            // 선택
      "salary": "6천~8천",                  // 선택
      "tags": ["프로덕트디자인"],           // 선택, 최대 8개
      "url": "https://...",                 // 필수, 지원/공고 링크
      "posted_at": "2026-07-28",            // 필수
      "expires_at": "2026-08-28",           // 선택, 지나면 목록에서 자동 제외
      "logo": "https://...",                // 선택, 회사 로고 또는 favicon
      "company_description": "회사 설명",    // 선택, 상세 페이지용
      "summary": "공고 요약",                // 선택, 실제 공고 내용 기반 요약
      "responsibilities": ["주요 업무"],      // 선택, 최대 8개
      "qualifications": ["자격 요건"],        // 선택, 최대 8개
      "preferred": ["우대 사항"],             // 선택, 최대 8개
      "related_links": [                     // 선택, 최대 6개
        {
          "title": "지원 전에 볼 자료",
          "url": "https://...",
          "source_name": "YouTube",
          "type": "youtube"                 // article | youtube | company | news | other
        }
      ]
    }
  ]
}
```

- `id`는 `YYYY-MM-DD-회사-포지션` 패턴을 권장합니다. **이전 날짜 파일과도 중복 금지**
  (validate가 전체 파일을 교차 검사합니다). 같은 공고를 다시 싣지 않습니다.
- 채용 목록에서는 회사 로고, 요약, 태그를 보여주고 `/jobs/[id]` 상세 페이지에서 실제 공고 요약,
  주요 업무, 자격 요건, 우대 사항, 관련 아티클/유튜브/회사 자료를 함께 보여줍니다.
  `url`은 반드시 실제 지원/공식 공고 링크여야 하며, 상세 내용은 공식 공고에서 확인한 것만 씁니다.

## 3. 게시 절차 (에이전트 체크리스트)

```bash
# 1. 최신 상태로
git pull origin main

# 2. 소스 체크 — 등록된 뉴스레터/미디어/VC/유튜브의 새 글 목록
#    (config/sources.json 이 소스 레지스트리)
npm run sources:check -- --days 2
#    "수동 확인 필요" 소스는 홈 URL을 직접 방문해 새 글을 확인한다

# 3. 후보 중 3~7건 선별 → 원문 확인 → WRITING.md 기준으로 아티클 작성
#    헬퍼: npm run new:article -- design my-slug "제목"

# 4. 검증 — 실패하면 고치고 다시
npm run validate

# 5. 커밋 & 푸시
git add content/
git commit -m "content: 2026-07-28 데일리 큐레이션 (아티클 4건, 채용 3건)"
git push origin main
```

선별 기준: 소스가 겹치면 **원문(1차 소스)** 을 `source_url`로 쓴다.
큐레이션 미디어(디자인나침반 등)가 다룬 글이라면 그 미디어가 아니라
원래 발표/아티클을 소스로 삼는다.

- 커밋 메시지는 `content: <날짜> 데일리 큐레이션 (아티클 N건, 채용 N건)` 형식.
- **확신이 없거나 에셋(이미지·영상)을 못 구한 글은 `draft: true`로 올립니다.**
  사람이 `/drafts`에서 검수하고 발행합니다. 반쯤 된 글을 피드에 올리지 않습니다.
- showcase 글의 이미지·영상은 `npm run assets:find -- <URL>` 로 추출합니다.
  접근이 막혀 실패하면 차단된 호스트를 그대로 보고하고 draft로 남깁니다 —
  프록시·캐시로 우회하지 않습니다.
- 코드(`app/`, `lib/` 등)는 절대 수정하지 않습니다. 콘텐츠 커밋은 `content/`만 건드립니다.
- 검증 실패를 스스로 해결할 수 없으면 게시를 중단하고 이슈를 남깁니다.

## 3.5 영감 피드 · 링크 모음 관리

### 영감 피드 (`content/inspiration.json`)

잘 만들어진 포스터/BI/인터페이스 이미지를 큐레이션하는 핀터레스트형 피드.

- `image`: **핫링크가 허용되고 출처가 명확한 이미지 URL만** (공식 프레스킷,
  브랜드 공식 사이트, 라이선스가 확인된 소스). 작가 개인 작업물은 원 게시물
  링크(`source_url`)를 반드시 달고, 문제 제기 시 즉시 제거한다.
- `id`는 유일해야 하며, 하루 2~4개 추가를 권장. `sample: true` 항목은
  실제 큐레이션이 5개 이상 쌓이면 삭제한다.

### 링크 모음 (`content/links.json`)

디자이너 필수 도구/사이트 모음. 자주 바뀌지 않는다 — 새 도구가 충분히
검증됐을 때만 추가하고, 그룹당 6개를 넘기지 않는다 (모으는 것이 아니라
고르는 페이지다).

## 4. 소스 선정 기준

- 디자이너에게 실질적으로 유용한가? (읽고 나서 행동이 바뀌는가)
- 국내 독자 기준으로 맥락 보충이 필요한가? (필요하면 코멘트 추가)
- 광고성/어뷰징 콘텐츠 제외. 채용 공고는 공식 채용 페이지 링크만 사용.

### 수집 소스

- **아티클 소스는 `config/sources.json`이 단일 목록입니다** (해외 소스만 등록 —
  뉴스레터/디자인 미디어/VC/유튜브). `npm run sources:check`로 새 글을 확인합니다.
  국내 미디어는 신뢰 소스 목록에 넣지 않습니다. 해외 소스를 한국어로 옮기는 것이
  crit의 기본 큐레이션입니다.
- 소스 추가/제거는 sources.json 수정으로만 합니다 (에이전트가 임의 소스에서
  수집하지 않습니다). 도구 공식 블로그의 대형 발표는 예외적으로 허용됩니다.
- **채용**: 토스·카카오·네이버 등 국내 공식 채용 페이지, 원티드, 디자이너잡,
  디자인루키 — 최종 링크는 반드시 **공식 채용 페이지** 또는 원 공고 URL

### 정확성 규칙 (중요)

- **검색 스니펫만으로 세부 사실을 단정하지 않는다.** 수치·날짜·기능명은 원문에서
  확인된 것만 쓰고, 확인 불가하면 뭉뚱그리지 말고 빼라.
- 오래된 뉴스를 "오늘/이번 주" 소식처럼 쓰지 않는다. 시점이 불확실하면
  시점 표현 없이 "왜 중요한가" 중심으로 쓴다.
- 채용 공고는 마감되었을 수 있다 — 지원 링크가 살아있는지 확실치 않으면
  회사 공식 채용 페이지를 링크한다.
- 같은 소식을 다룬 아티클이 이미 있으면 다시 쓰지 않는다 (`content/articles/`
  전체에서 제목·태그로 확인).
